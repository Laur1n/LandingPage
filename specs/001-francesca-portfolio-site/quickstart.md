# Quickstart: Validate the Francesca Simone Portfolio Site

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This guide proves the feature works end-to-end. It assumes the implementation tasks (`tasks.md`,
generated by `/speckit-tasks`) have been completed. It does not duplicate field-level details —
see [data-model.md](./data-model.md) and [contracts/](./contracts/) for those.

## Prerequisites

- Node.js 22 LTS and npm installed locally.
- A **public** GitHub repository containing this project, with GitHub Pages enabled (Settings →
  Pages → Source → "GitHub Actions") and `.github/workflows/deploy.yml` present (research.md §5).
- A DecapBridge account with this site registered, and Francesca's admin user invited
  (research.md §3).
- No environment variables or secrets to configure — GitHub Actions deploys with its own built-in
  credentials, and there is no export function or build-hook to wire up (research.md §6/§7).

## 1. Local setup

```bash
npm install
npm run dev
```

Expected: the public site is served locally (default Astro dev port) with all baseline sections
rendering placeholder/seed content from `src/content/`.

## 2. Exercise the admin editing flow locally

```bash
# In a second terminal, with Decap CMS's local backend enabled for development:
npm run dev
# Visit /admin/ (trailing slash matters — see step 3) — with `local_backend: true` in
# public/admin/config.yml during development, Decap CMS reads/writes src/content/ directly on
# disk instead of via git-gateway.
```

Validation steps (maps to US2/US3 acceptance scenarios):

1. Open `/admin/`, add a new tour date (venue, location, date/time). Save.
2. Confirm the change is _not_ yet visible on the running public site preview (draft/publish
   separation, FR-019) when running against the real (non-local) backend; in `local_backend` mode
   this step is illustrative only, since local mode writes directly to disk for fast iteration —
   the draft/publish gate is validated for real in step 4 against the deployed site.
3. Use the "Preview" action and confirm it shows the change rendered in-app, styled with the
   site's real fonts/colors (research.md §2 — this is not a live deploy-preview URL, since GitHub
   Pages doesn't provide one).
4. Publish. Confirm the change now appears on the public site once GitHub Actions finishes
   redeploying.
5. Repeat for one entry in each of: biography, projects, discography, teaching, contact,
   Impressum/Datenschutz — confirming each publishes independently (US3 AC1–AC7).

## 3. Validate authentication boundaries (FR-012, FR-014, SC-006)

```bash
npm run build && npm run preview
```

1. Visit the built site's `robots.txt` — confirm `/admin/` is disallowed.
2. View page source of `/admin/index.html` — confirm a `noindex` meta tag is present.
3. Confirm no public navigation link points to `/admin/`. Note the trailing slash matters: on
   GitHub Pages, `/admin` (no slash) 404s, since only `admin/index.html` exists — always link to
   or type `/admin/`.
4. Attempt to call the Decap CMS backing API without a valid session token (e.g., via `curl`
   against the `git-gateway`/DecapBridge endpoint) — confirm the request is rejected (401/403),
   proving unauthenticated writes are impossible.

## 4. Validate content export (FR-021)

1. Without logging in anywhere, visit
   `https://github.com/<OWNER>/<REPO>/archive/refs/heads/main.zip` in a browser.
2. Confirm a ZIP of the full repository downloads immediately (contracts/export-content-api.md).
   No admin session, button, or token is involved — this works purely because the repository is
   public (a GitHub Pages hosting precondition, research.md §5).

## 5. Validate tour-date freshness (FR-005)

1. Publish a tour date with a `date` a few minutes in the future.
2. Wait for it to pass.
3. Either publish any unrelated content change, or wait for the scheduled daily GitHub Actions
   run (`.github/workflows/deploy.yml`, `cron: "0 3 * * *"`) — or trigger it manually via the
   "Run workflow" button in the Actions tab — and confirm the now-past date no longer appears in
   the public "upcoming" list without any manual deletion.

## 6. Validate baseline content coverage (Principle V, SC-001)

Cross-check the deployed homepage and footer against the current site
(https://jazz-isses.de/Francesca/) section by section: Vita, Projekte, Termine, CDs, Unterricht,
Kontakt, and the newly-added Impressum/Datenschutz. Every section MUST be present and reachable.

## 7. Validate performance and accessibility (SC-002, SC-003, SC-009)

```bash
npm run build
npx playwright test        # runs the e2e suite, including @axe-core/playwright checks
```

Also run a Lighthouse pass (mobile) against the deployed production URL and confirm:

- Performance score ≥ 90.
- No critical Accessibility issues (target WCAG 2.1 AA, FR-022).
- The homepage's next upcoming concert date is visible/locatable within 10 seconds of a manual
  timed walkthrough (SC-002 is a UX timing target validated by manual test, not purely automatable).

## 8. Validate the "no developer needed" promise (SC-004, SC-005, SC-007)

Have Francesca herself (not a developer) perform, unassisted:

1. Add/edit a tour date end-to-end (login → edit → preview → publish) and time it — target under
   5 minutes (SC-004).
2. Edit one non-date content item (bio, a project, a discography entry, teaching info, a contact
   detail, or the Impressum text) end-to-end and time it — target under 5 minutes (SC-005).
3. After some real-world use, check in with her (SC-007) on whether she felt she could maintain
   the site without asking for developer help.

## Done

All steps above passing constitutes a successful validation of this feature against its spec.
